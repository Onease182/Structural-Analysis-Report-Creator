### 1. `tools/inventory_template.py`

**Purpose.** Reads DOCX OOXML and inventories document-body paragraphs, tables, images, fields, and section breaks. It writes JSON and Markdown inventories, a placeholder registry, and decision notes. It does not connect to ETABS, extract results, or calculate structural quantities.

**CLI.** No positional arguments. Options: `--input PATH` (default `Chatra Bahadur Ramtel.docx`), `--json PATH` (default `docs/template_inventory.json`), `--markdown PATH` (default `docs/template_inventory.md`), `--registry PATH` (default `docs/placeholder_registry.yaml`), `--decisions PATH` (default `docs/needs_my_decision.md`), and `--force`. If any target exists and `--force` is absent, exit code 2. Caught DOCX/XML errors also return 2. Outputs are written sequentially, not as one atomic transaction.

**Inputs and dependencies.** Required DOCX with `word/document.xml` and a `w:body`; `word/styles.xml` is optional. `word/_rels/document.xml.rels` is read unconditionally. Uses Python standard library plus third-party `lxml.etree`; no Word COM, `python-docx`, Excel, ETABS, or YAML library is imported. It does not read a spreadsheet, CSV, project configuration, ETABS model, or project brief.

**Outputs and schemas.** Defaults are `docs/template_inventory.json`, `docs/template_inventory.md`, `docs/placeholder_registry.yaml`, and `docs/needs_my_decision.md` (all overridable). JSON has `source`, `statistics` (`paragraphs`, `tables`, `images`, `sections`, `items`), and item records with fields such as `index`, `type`, `style_name`, `section`, `text`, `text_preview`, and classification, plus type-specific metadata. Table item metadata includes `rows`, `columns`, `header_row`, `number`; image metadata includes `relationship_id`, `target`, `alt_text`, `title`, `doc_property_id`, dimensions in EMU and inches. The registry is YAML serialized by in-file code, with root `items` and entry fields `key`, `description`, `type`, `unit`, `source`, `required`, `example`; it also adds 18 owner registry entries. Markdown is an outline/inventory. Decision notes are Markdown. No CSV is read or written.

**Assumptions, gaps, and conditional portability.** Rules are sample-template-specific: Table 3 fill rows; Table 5 expected 3×3 shape and fixed code/parameter plus project-value column; paragraph ordinals 161/162; staircase body-child indices 370–374 and inventory indices 516, 518, 520, 522, 523, 530; and specific heading, clause, foundation-reaction, and irregularity text. Insertions/reordering can invalidate ordinal rules. No `EQX-ULS`, `EQX-SLS`, `Rmu=4`, `kd=0.94`, storey count, seismic zone, or NBC design calculation is present. A `source: excel` or numeric registry type can be inferred heuristically rather than confirmed. `classify` accepts “no soft stoy” and “no soft story,” while `apply_template_rule` matches only the misspelling; correctly spelled text may classify `COMPUTED` without its computed-variant template rule. A paragraph is recorded before nested image/field events and mixed text is not unified into exact interleaving; tab/line-break markers are literal backslash sequences before normalization. `section_number_for_body_child` is unused. `--force` does not implement generated filename/diff summary, special protection for the curated registry, or a “regenerated by Word” mark. No testing, provenance/conflict handling, unresolved-item list, ETABS, Excel, or NBC logic exists.

Different storey counts are not represented by a storey-aware row schema. Basement is only a conditional keyword, without level convention or basement rules. No zone parameter or zone validation exists. The code’s sample-index and language assumptions may silently attach to wrong material for a changed template. Missing `.rels` can fail the inventory. These are code limitations, not claims that a particular DOCX run failed.

### 2. `etabs_extract_tables.py`

**Purpose.** Attaches to the currently open ETABS model; may run analysis/design; extracts configured ETABS tables, writes CSVs and an Excel workbook, exports `.e2k`, and builds geometry and column-location data plus diagnostics. It does not implement NBC 105:2025 calculations or final report assembly.

**CLI.** No argparse CLI; run as `python etabs_extract_tables.py` with no arguments. Configuration is in module-level constants. Main execution is guarded by `if __name__ == '__main__'`.

**Inputs and dependencies.** Requires Windows, a compatible open ETABS model/API exposed through `CSI.ETABS.API.ETABSObject`, `comtypes`, `pandas`, and `openpyxl`; versions are not pinned. Reads model tables, filename, cases, geometry, units, and state. It sets units enum 6 (commented `kN-m-C`) during extraction and attempts restoration. Analysis and concrete design can run automatically if model state/tables indicate need. E2K export and API geometry fallback are enabled by defaults. It reads no CLI file, workbook, project config, or project brief.

**Outputs and schemas.** Files go to `<script directory>/tables/`. It writes `etabs_tables.xlsx` if any table/geometry result exists; worksheet names are truncated to 31 characters. Configured fetched tables create `<table-key>.csv` when available, including (among others) `01_Modal_Periods.csv`, `02_Modal_Mass_Ratios.csv`, `03_Base_Reactions.csv`, `04_Story_Drifts.csv`, `05_Story_Forces.csv`, `07_Column_Design.csv`, `08_Beam_Design.csv`, `07b_Column_PMM_Env.csv`, `07c_Column_Shear_Env.csv`, `08b_Beam_Flexure_Env.csv`, `08c_Beam_Shear_Env.csv`, `09_Centers_Mass_Rigid.csv`, `10_Story_Stiffness.csv`, `11_Joint_Reactions.csv`, `12_Story_Definitions.csv`, `13_Grid_Definitions.csv`, raw `14_Joint_Coordinates_raw.csv`, connectivity/assignments/material/load/response-spectrum/mass-source tables, and `31_Joint_Drifts.csv`, `32_Joint_Displacements.csv`, `33_Story_Max_Avg_Displacements.csv`. Actual presence is ETABS- and version-dependent. Additional area-section output can be `23x_<sanitized table name>.csv`.

Geometry package CSV schemas: `14_Joint_Coordinates.csv`: `Joint`, `GlobalX`, `GlobalY`, `GlobalZ`, optionally `Story`, `Label`; `29_Frame_Members.csv`: `Frame`, `Type`, `JointI`, `JointJ`, `Story`, `Section`, `Width`, `Depth`; `30_Slab_Panels.csv`: `Area`, `Type`, `Story`, and `Joint1…JointN`; conditional `34_Column_Locations.csv`: `Label`, `Story`, `UniqueName`, `X`, `Y`. `available_tables.csv` has `table_name`, `table_key`; the workbook/CSVs preserve dynamic ETABS column names. `extraction_manifest.json` records timestamp, model, units enum, run flags, counts, diagnostics, configuration, E2K/geometry/column status, and per-table status, ETABS name/key, rows, columns, and filters. The raw joint CSV is replaced by the normalized geometry package CSV. Prior geometry/ULS package CSVs listed in the audit are deleted at startup; other stale table CSVs are not cleaned.

**Assumptions, engineering values, and portability.** Configured seismic cases are `EQX-ULS`, `EQY-ULS`, `RSX-ULS`, and `RSY-ULS`; base reactions also use `Dead`, `Live`, `DL + LL`; the narrowed ULS drift/displacement/torsion data selection uses only `EQX-ULS` and `EQY-ULS`. These are module configuration, not automatic discovery. No `Rmu=4`, `kd=0.94`, fixed three-storey assumption, zone, or NBC limit is implemented; the console notes that the report applies Rμ but no factor is defined here. Torsion console diagnostic uses `r/(2-r)`, assumes `Min=2*Avg-Max`, and prints thresholds 1.5 and 2.5; it is not an NBC pass/fail calculation. Geometry classifies frames by vertical versus horizontal plan length; areas by Z-range; e2k export tries enum candidates `[3,2,1]` with header markers. Table names/fields depend on ETABS version; returned columns are dynamic.

Different storey counts are generally ETABS-driven, but this script does not check complete story coverage or reconcile stories with geometry. No basement convention or zone parameter exists. A different model’s case labels or combinations can produce missing/empty filtered outputs. API tuple signatures and table names may vary. Geometry can be incomplete when recognized columns/connectivity are missing, and returned data may not agree across model tables. The script deletes selected output files before confirming connection, while stale non-package CSVs can remain. Excel sheet-name or sanitized area-table filename collisions are possible.

Drifts loop over discovered stories, not fixed three, but floors in schedules use a finite Ground–Twelfth naming list then `Floor N`; ordering/height reconstruction can fail with inconsistent stories. Basement height can be included in H and limits; elevation fallback assumes datum zero. ULS stories/heights reuse SLS-derived stories, so mismatches can omit/misalign rows. Zone/site parameters are absent, so same configured limits/factors apply unless overridden. Corner/edge method uses convex hull and falls back to all joints when coordinates are inadequate. Optional/missing schemas may skip panels or cause rendering failures; CSV read errors can be silently treated as missing. Inference of reinforcement units, ratios, grid labels, and bar requirements needs project-specific validation.

### 7. `generate_structural_report.py`

**Purpose.** Compiles `report_data.json` into an editable DOCX with cover, fixed narrative, extracted tables, live TOC/page fields, and appendices. Does not query ETABS, calculate response, emit CSV/XLSX/PDF, or fill/preserve the master template format.

**CLI.** `--input PATH` (default `validation/report_data.json`), `--output PATH` (default `report/structural_analysis_report.docx`), `--title` (`Structural Analysis and Design Report`), `--project` (defaults to extraction filename stem or `Structural Project`), `--author` (`Structural Engineering Consultancy`). No zone, storey, case, `Rmu`, `kd`, or units options.

**Inputs and dependencies.** UTF-8 JSON with expected nested `extraction`, `validation`, `geometry`, `inputs`, `analysis`, and `design` objects. Uses python-docx and Python standard library. No ETABS, pandas, Excel, or automated Word/LibreOffice field-update dependency; user must update TOC/page fields in Word/LibreOffice. Input JSON is not comprehensively schema-validated.

**Outputs and data columns.** One DOCX, default `report/structural_analysis_report.docx`, parent directory created. It has dynamic local date, fixed revision R0, chapters 1–11 and appendices A–E, live TOC and PAGE/NUMPAGES fields. No other output. Fixed selected table headers include validation `Status | Table | Message`, modal `Case | Mode | Period | Frequency`, drift `Direction | Drift`, centers/rigidity `Story | Diaphragm | XCM | YCM | XCR | YCR`, and key/value `Item | Value`; dynamic inventory/governing tables use JSON record keys. Display caps include general 30, checks 60, appendices commonly 20/25/40; modal, drift and center tables 20. Truncation notice points to `report_data.json` for full records.

**Assumptions, engineering values, and portability.** Narrative statically names EQX-ULS/EQY-ULS, says there is no response-spectrum output, and asserts 12 modal modes; it does not verify these against input. It references IS 456-2000 and NBC 100/102/103/105 text requiring confirmation; it is not a demonstrated NBC 105:2025 check. It contains no `Rmu=4`, `kd=0.94`, `EQX-SLS`, zone, unit conversion, storey-specific calculation, or limit. Fixed English title/header, R0, Aptos styling, confidentiality footer, local date and chapter structure. For other zones/cases, static claims may be false. Basement/story records can be shown without semantic classification; no story matching validation. DOCX tables may truncate at row caps. Malformed JSON or wrong nested types can fail. Report content is distinct from the owner's master template and does not implement owner decisions about conditional staircase removal or computed paragraph variants.

The following is the apparent data flow from filenames and responsibilities, not a verified orchestration command. The scripts are independently invoked; the sparse README documents no run sequence, and no supplied audit establishes that every stage currently runs successfully end-to-end.

## Explicit integration risks and unresolved contracts

1. **No documented orchestration or reproducibility contract.** README supplies only a title. There is no verified setup/run order, dependency lockfile, Python version guarantee, or end-to-end test. Scripts use relative paths differently (current-working-directory defaults versus script-relative output directories), creating path-selection risk.
2. **Two extraction branches are not interchangeable without adaptation.** `etabs_extract_tables.py` emits `04_Story_Drifts.csv`, `14_Joint_Coordinates.csv`, `extraction_manifest.json` and geometry package names; SLS extractor emits `S01_Story_Drifts.csv`, `S12_Joint_Coordinates.csv`, `sls_extraction_manifest.json`. The report reader supports some aliases, but the validator's fixed table schema expects the non-S-prefixed package. The SLS extractor does not provide all geometry/design inputs needed by the general validator/report and reinforcement stages.
3. **ETABS case disagreement.** General extraction config includes EQX/EQY and RSX/RSY ULS, with ULS package filtering narrowed to EQX/EQY. SLS extractor defaults to EQX/EQY SLS and EQX/EQY ULS. Report calculator uses these defaults plus `Rmu=4`; the DOCX narrative statically claims EQX-ULS/EQY-ULS and no response spectrum. Inventory merely includes sample clauses/text. Case identities, analysis purpose, and availability must be verified per model; none of these names constitutes a zone parameter.
4. **Manifest and schema mismatch potential.** Dynamic ETABS fields are passed through, while validator, figure/report scripts expect specific column names and aliases. Validator's manifest-driven table list can displace its fallback required set. Its validation checks only file read, required-column presence, and emptiness—not units, nulls, value ranges, completeness, physical consistency, or case provenance. A “PASS” is not engineering approval.
5. **Units are inconsistent as contracts.** Extractors set enum 6 with comment `kN-m-C`; SLS extractor documentation says metres but does not convert; validator passes through values; figure generator uses unverified unit labels and fabricated dimensions; SLS report assumes metres for drift/displacement, section values, and building height while also using heuristics for areas/shear. No shared machine-enforced unit metadata/schema guarantees compatible values across paths.
6. **Risk of double/missing scaling and misapplied defaults.** Table extraction reports unscaled ETABS results. SLS extraction explicitly describes no scaling. `generate_sls_drift_report.py` multiplies ULS demand by default 4.0 (`--uls-scale`) but defaults compliance `--kd` to 1.0, while `--kd-info` is 0.94. Other scripts contain no such factors. Do not apply report outputs as though the extraction stage had scaled them; independently verify requested scaling, model system, and policy before engineering use. The supplied evidence does not establish a universally applicable `Rmu=4` or `kd=0.94`.
7. **Storey, basement, and zone generality is not end-to-end.** Inventory rules include fixed sample paragraph/table/index assumptions; extractors do not establish a basement policy; validator aggregates supplied story rows; figure inference assumes regular geometry and drops lowest-elevation panels; report calculator sums story heights and reuses SLS stories for ULS; DOCX narrative does not validate stories. There is no zone/hazard/site input, zone-dependent calculation, or common storey/basement contract. Different building counts may parse but that is not evidence of correct checks.
8. **Owner decisions are not wired across artifacts.** Inventory records classifications/decisions but is not a transformation engine. The DOCX generator is not connected to placeholder registry, owner context, or template and has hard-coded contradictory/sample statements. Staircase conditional removal, foundation wording, variable clause mapping, irregularity conclusion variants, and retained-image/variable-combination decision require explicit implementation downstream. The two pending conditional decisions remain unresolved.
9. **Output freshness and cleanup hazards.** General extractor deletes selected geometry/ULS CSVs before connection; SLS extractor deletes all matching S-prefixed CSVs and workbook/manifest before extraction; other table CSVs may remain stale. Figure generation overwrites PNGs but can skip missing inputs and still return success. Validation/report outputs may therefore combine missing or stale files unless orchestration gates on manifest timestamp, model identity, case filters, and completeness. `.gitignore` hides several generated trees from ordinary version control.
10. **Output contracts are not unified.** Figure outputs are conditional, drift summary may omit torsion, reinforcement schedules may be skipped, DOCX has row caps, while downstream callers may assume files exist. No common run manifest links generated figures, validation JSON, SLS results, and DOCX to the same model/configuration.
11. **Runtime compatibility and dependency risks.** Windows ETABS COM scripts are platform-specific; other scripts use Python 3.10+ syntax. Supplied audits flag nested-quote f-string compatibility in validator and potentially Python 3.12+ syntax; target interpreter is not specified. pandas/matplotlib/openpyxl/python-docx/lxml versions are not pinned. ETABS COM tuple layouts and table names are version-dependent.
12. **Engineering authority/provenance gap.** No supplied script provides a complete provenance/conflict-resolution system, engineering UNRESOLVED register, full NBC 105:2025 calculations, or verified source-of-truth hierarchy. The DOCX contains static code narratives and the drift calculator contains defaults/commentary; neither proves code correctness. Treat every computed or displayed quantity as requiring traceable input, case, unit, formula, and engineer review.

## Phase 0 conclusion

The repository contains useful but loosely coupled stages: DOCX inventory, two ETABS extraction paths, CSV schema/descriptive validation, figures, a drift/design report calculator, and a separate JSON-to-DOCX compiler. Their outputs and filenames overlap only partially. Existing code makes sample-specific assumptions and leaves key contracts—especially case naming, units, scaling, basement/story treatment, zone inputs, data provenance, and owner-decision implementation—unverified. The owner decision log should constrain later design, but its decisions are not proof that the current scripts implement them. Before operational or engineering reliance, establish a single explicit configuration/schema/provenance contract and test it against representative models; do not infer or add engineering values from this audit.
